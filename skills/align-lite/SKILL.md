# Align Lite

做一件事：**在写代码之前把问题问出来。** 问题发现得越早，后面越不需要流程。
一份需求最多新增 1 份 md（交付说明），其余不落盘。

**什么情况不用这个 skill**：改 typo、一行逻辑错、需求已明确到字段且不会误解、纯问答、查 bug。这些直接做。

## 第 1 步 · 对齐需求（对话里做；对齐完就把结论写进交付说明 §1）

把这段打出来让用户确认：

```
    ┌ 你要的效果 ──────────────────────────────
    │ 客户场景：<谁在什么情况下遇到什么>
    │ 改完后：<用户能看到什么变化>
    └ 本次不做的：<明确排除的，防止越界>
    范围对不对？
```

**什么算确认**：用户明确说出“范围对/可以做”，或指出要改的点。
**什么不算确认**：`好的` / `嗯` / `你继续` / 只回一个表情。不算就要继续问，但不能重复问同一句——换一种问法，或先给出你的假设让他纠正。

确认后，把这段**原样搬进交付说明的 §1**（那时交付说明刚建立，只填 §1）。

## 第 2 步 · 讲清 + 确认（唯一的一关）

这一关同时解决两件事：**用户不熟悉的旧逻辑**，和**还不知道的风险点**。都在对话里做，不落盘。

### 2.1 怎么讲 —— 用伪代码，不用抽象描述

```
把这次改动（或这段旧逻辑）写成伪代码

if 伪代码 ≤ 20 行:
    直接发伪代码，问"这段看懂了吗"
else:
    先发分段表（每段一行，≤6 行），等用户点某段：
    ┌ 段落            它干什么                        要你拍板吗
    │ ① 检测低速率    每秒扫一遍在线终端，数连续低几次     否
    │ ② 进低速库      凌晨把名单批量写进 mac 库           否
    │ ③ 角色怎么生效  踢掉重连后角色会不会重算            ★ 是
    └ 本次不碰：AD 认证流程、Web 页面
    用户点"③" → 只展开 ③ 那一段的伪代码（≤20 行）

展开某段时，若那段有取舍：
    在同一条消息里给出
        做法 A（我建议）：<一句话>   理由：<一句话>
        被否的 B：<一句话>           为什么否：<具体后果>
    停 → 等用户回答（一轮只发一条）
```

**逐条讲的时候，一轮只发一条，发完就停。** 用户说“我跟丢了”→ 只补讲缺的那个前提（≤8 行），然后重发同一条；不要重发全文。

**旧逻辑怎么查**：委派 Explore 子 agent 去读代码（自己不读，保住主线程上下文）。要求它只回四栏：`问题 / 结论一句话 / 依据（符号名 + 能复现的命令或日志片段）/ 它没查的`。**不让它写任何文件。**

**什么叫讲完**：用户能用自己的话把这次改动的效果说出来，且包含三样东西——**改完是什么效果 / 哪些行为不变 / 失败时会看到什么**。三样缺一，就补讲同一条，不进下一条。

### 2.2 取舍的门槛 —— 什么算"要你拍板的事"

满足**任意一条**就算：

- 会影响用户能观察到的行为（日志、页面、终端能不能上网）
- 需要新增或改动数据结构（字段、表、proto）
- 存在两条都能实现的路子

不满足的（命名、变量类型、函数拆分）自己定，不要问。

### 2.3 风险清单 —— 逐条验证，任何一条不成立就当场改方案

验证方式只有三种，必须留下痕迹：**①跑一条命令留输出 ②读实现并引原文 ③用户答复原文**。

> 这条清单来自实际踩过的坑，不是设计出来的。每条后面的例子都是真实发生过的。

| 问 | 怎么验 | 真实踩坑的例子 |
|---|---|---|
| 1. 这个方案依赖设备的哪些**跑起来才知道**的行为？ | 实机一条命令 + 看日志 | "踢掉用户后 15 秒内重连会走漫游、沿用我们改好的角色" → 实测不成立：portal/PSK 漫游会**强制还原旧角色**，整条踢人路线作废 |
| 2. 我依赖的每个接口，**真实**返回值/副作用是什么？ | 读**实现**，不读注释、不读文档 | 某接口**恒返回 0、不检查内层返回**（吞错误）→ 撞容量上限时**静默失败**；而文档写的是相反的"会整批回滚" |
| 3. **上限 / 超时 / 看门狗 / 容量**是多少？超了会怎样？ | grep 常量 + 看错误分支 | 单批上限 64、心跳看门狗 35 秒会被杀进程、mac 库全局上限 60000 撞上静默失败 → "凌晨一次性写全表"直接打爆 |
| 4. 需求里的**名词**与**失败路径**，边界情况定义了吗？ | 逐条问用户 | "超过阈值"算不算包含等于 / 中途下线算不算 / 速率恢复要不要移出 / 写库成功后表清不清——4 个空档，答案不同功能完全不同 |
| 5. 依赖哪些**我们控制不了**的东西？失败看得见吗？ | 自问三个问题（见下） | 依赖"客户手动断开无线、且间隔 >15 秒"重连才拿到角色；手机常自动回连落在 15 秒内，**失败还不报错** → 应当直接否决 |

**问 5 的"失败看得见吗"怎么判**：
- 失败时调用方能拿到非 0 / 非 OK 吗？
- 有日志，且日志里有能分清成败的字段吗？
- 失败后系统状态会与预期不同、却不被人察觉吗？

三问只要有**一问答"否"**，就算存在静默失败，这一条不成立。

**问 5 不成立怎么办**：先问用户"这个外部依赖能不能去掉，或者能不能改成可观测"，两条都不能 → **停手，回报**，不要自己硬做。

> ★ 以后遇到**新类型**的坑 → 往这张表里**加一行**（一次一行），并当场告知用户加了什么。不写报告、不建档。
> ★ 加之前先自问：**没有这条，agent 会做错吗？** 不会 → 删掉它，别加。

### 2.4 讲给用户听的话，怎么写

🔴 **不准自造名词。** 只有我说过、用户没确认过的词（包括我上一轮临时造的名字）**一律不许出现在面向用户的文字里**：要么用一句大白话替代，要么在同一个句子里解释。这条不看情况、不看篇幅——它是“发送前自检”的第一条。

- **先说人话，再说术语**。顺序固定：业务后果 → 机制 → 代码符号。永远不要用符号开头。
  ✅ `断开超过 15 秒（配置项 rj_t 的默认值），这条"当成老用户"的通道就关了。`
  ❌ `rj_t 一过，通道自动关闭。`
- **主语用角色**（WAC / 网点 / AP / 终端 / 用户），动作写在动词里。不要"进行优化""作出判断"。
- **不要自造的图例**。不要 `✅已证实｜⚠️强推断｜❌已废弃` 这种符号系统；把"这条是实机测过的""这条是我推的没跑过"直接写在每条旁边。
- **删掉元数据前置**。分支名、commit、日期、"本件为 v1""修订说明"一律不进开头，放文末或干脆不放。
- **改了主意就说"我原来以为 X，其实是 Y"**。这是让读者敢质疑你的最有效一句话。
- **因果、取舍、为什么 → 必须用散文**（`因为 / 但是 / 除非` 这些连接词就是信息本身，列表会吃掉它们）。
- **真假并列的集合、必须按序的步骤、条件与例外 → 才用列表**。用之前先试试能不能写出引导句：能写出"这次一共动到三处："就是真列表；只能写出"以下几点："说明它们之间有被藏起来的关系，改成散文。
- **因果链、时间线、状态变迁不许用表格**；表格只用于"多个维度同时可比"。
- 写成一段话超过 **400 字**就先拆成两轮，不要一次发完。

> 🔴 **发送任何面向用户的解释/建议之前，先过一遍 `references/讲解语言规范.md` 第零节的「发送前自检」** —— 名词结算表（U=用户说过 / D=本条内定义 / C=他的职业常识 / **X=只有我说过→必须为 0**）→ 七检 → 三条硬闸；面向用户的解释默认用「前提 / 事实 / 建议 / 问题」四行。
> 该文件后面还有：30 条改写手法、中文常见的 8 个坑、6 段讲解骨架、正反例对照。

## 第 3 步 · 写代码（先空壳、后实现）

**动手前先做两件事**（这两件都写在 `D:/fhy_knowledge_database/定制/AGENTS.md` 里，只读指针不拄规则）：

- **先合历史定制，再写新代码**（R1 按产物 / R2 整文件 `git checkout` 绝不挑 hunk / R3 新代码后落）+ 三闭包 + 必查 5 项——见 `定制/AGENTS.md` §5。不先合就会锚点撞车、反复返工。
- **代码规范**：定制代码标 `/* [DINGZ] custom: <客户>-<需求号> begin/end */`；日志 `[DINGZ]` 前缀、高频路径禁逐条打印、不打印密码/完整 MAC；提交以 `[Wlan-YYYYMMDDNN] ` 开头（单号从项目文件夹名首段取）——见 `定制/AGENTS.md` §2 §6 §9。

**新增文件**：先只交空壳，确认结构对了再填实现。

```c
/* TODO(<需求号>): <这个函数负责什么> */
int lowrate_calc_role_for_terminal(const char *mac      /* 终端 MAC */,
                                   unsigned int rate_kbps /* 当前速率，单位 kbps */)
{
    assert(0);        /* 空壳占位：填实现时删掉这一行 */
    return -1;
}
```

- 署名写**需求号**（如 `Wlan-2026081401`），不写人名。
- 空壳只要求**能编过**（`make`）。
- 🔴 **空壳禁止部署到设备、禁止拉进 valgrind 门禁** —— 真机上 `assert(0)` 不是占位符，会把守护进程打崩。
- "结构对了"= 把空壳的 diff 贴给用户，得到"结构对"的明确答复。

**改既有文件**：先只加函数签名和调用点，再填实现。

**设计写进文件头注释，一块不超过 15 行**，只写代码里看不出来的四件事：

```c
/*
 * 职责: 终端速率低于阈值时，给它分配低速率角色并下发限速。
 * 数据流: 认证完成 → 本模块算角色 → lowrate_cache 落缓存 → lowrate_flush 下发数据面。
 * 不变量: 缓存里的角色必须与在线用户表一致；不一致以在线用户表为准。
 * 不可简化: 不能把限速改到数据面按实时速率判定，因为数据面拿不到角色上下文，
 *           会导致限速抖动，并产生第二处一致性来源。
 */
```

- 四个标签固定：`职责 / 数据流 / 不变量 / 不可简化`，每个标签 ≤3 行，整块 ≤15 行。
- 改动横跨多个文件时，**只写在主改动文件**，其余文件留一行指向它。
- `不可简化` 必须写成 `不能改成<更自然的写法>，因为<实测后果>`，两段缺一不算写完。

**函数体内默认 0 行注释。** 只在"不显然"处写 why。判断标准是三问，任一为"是"才写：

- 后面的人会不会问"这里为什么这样写 / 为什么不那样写"？
- 我写的是 why 还是 what？
- 删掉这句注释，有没有人会改错？

**被否掉的路子留一行**：`/* 否：<具体做法>，会<具体后果> */`。超过一行 → 写进知识库，不要堆在代码里。

**不许写进注释**：本次需求的整体路线选择（那是交付说明 §2 “决策”的事）、变更历史、实现步骤、“第 1 步…”、代码行号、“已废弃”段落、显而易见的 what。

## 信息放哪

先记住一条总判据：**下面这些载体的默认读者都是“本需求链路上的人”。读者一旦在链路之外（客户、现场、下一位复核者、另一个团队），就得换载体。**

### 需求级：四个载体

按“这条信息下次被谁消费”来判断，不要按信息形式判断：

- **改这段代码的人要看的**（这段怎么走、不变量、为什么不能简化） → 代码注释。**头注释的 `职责` 行要说清“给谁解决什么问题”**，否则后来的人会当成无用代码删掉。
- **下个客户/别的项目还会遇到的机制**（跨模块时序、被否掉的路子、术语） → 知识库，每个主题一份，下次就地改，不新增第二份
- **只是想追溯“谁在什么时候改了什么”** → commit message（写完就完，不维护 CHANGELOG）
- **要做到什么功能 / 验收怎么算 / 选了哪条路、否了哪条 / 怎么装与回滚 / 还剩什么没结** → 交付说明

### 项目级：第 5 个载体（它不算“需求级”的 1 份配额）

**项目坐标文件** = 项目目录下的 `AGENTS.md`（`定制/AGENTS.md` §8 早就规定了它，只是上一版漏登记了）。只放那些**只对这一个项目成立**、又不属于任何一个需求的东西：

- 客户 / 型号 / 基线分支 + 基线 commit / 设备地址
- **历史定制包清单与打包装载顺序**（包括“必须先打 A 再打 B”这种依赖）
- 项目专属禁区（哪些宏/文件不能碰、哪些看起来能改其实会炸）
- 历史避雷与复用指针（“改 X 类功能前先看 Y”）；以后碰到仓库级避雷就往这里加
- 本项目的黑话 → 大白话对照（含“不要叫它”）

**什么时候写**：开工时就建（不是等到交付）；每碰到一条新的项目专属避雷就加一行。

### 不算载体：三类“输入/装置”（不进上面任何一个，也不受 1 份配额约束）

- **需求原始输入**（客户原话、临时口述）——它含大量噪声，不入载体；需要时按原文归档。
- **凭据与现场配方**（密码、key、共享密钥）——**严禁进任何载体**（含知识库/交付说明）；写在项目目录的 `debug.md` 一类现场文件里。
- **仓库级装置**（工具脚本与夹具、编译环境坐标、任务的并行拆分与依赖）——它们是执行的工具与临时结构，不是文档产物。工具脚本随项目存放，**在交付说明的证据索引里登记一行用法**。

冲突时以后者为准：同一件事在知识库和代码注释里说法不一致 → **当场合并或删掉一处，不要加“已废弃”横幅掩盖**。

## 收尾自检

- 本次新增的 md 文件数 ≤ 1？（就是那份交付说明；知识库里就地修改已有文件不算新增；**项目坐标文件 `AGENTS.md` 不算**）
- 项目坐标文件更新了吗？（本次碰到的新禁区 / 新的历史包顺序依赖 / 新的黑话）
- 交付说明的 §1（要做到什么 + 验收）和 §2（决策）是不是在过程中就填了，而不是事后回忆编出来的？
- 那 5 条问是不是每条都有痕迹（命令输出 / 引用的实现原文 / 用户答复原文）？
- 每条结论是不是都能落到上面四个地方之一，没有"只在对话里说过"的？
- 有没有留下"如上所述""刚才提到的""见第 3 条"这类只有本会话能懂的指代？
- 交付说明里"没测什么"是不是具体到场景，而不是"无"？

任一条不过 → 当场改，不要进入交付。
