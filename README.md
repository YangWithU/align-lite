# align-lite

pi 极简对齐包。取代 `align-together`（那个包已停止加载，目录保留）。

## 它是什么

**四步 + 一张 5 条清单。** 没有插件代码、没有门禁、没有目录约定、没有状态文件。

1. 对齐需求（对话，不落盘）
2. **讲清 + 确认**（唯一一关，`SKILL.md` 的 2.1–2.4）
   - 用**伪代码**讲逻辑；伪代码 >20 行时先发一张**分段表**，用户点哪段展开哪段
   - 取舍有门槛（影响可观测行为 / 动数据结构 / 两条路都行），才拿去问
   - 逐条验证 **5 条风险清单**，不成立就当场改方案
   - 面向用户的讲话规则（先人话后术语、不用自造图例、因果与取舍用散文）
3. 写代码（先空壳后实现，设计写进文件头注释 ≤15 行）
4. 交付（1 份交付说明，5 节）

**一个需求最多产 1 份 md。**

## 为什么把门全删了

| 理由 | 实测依据 |
| --- | --- |
| 门从来没工作过 | 首个方案签字后门就永久全放行（门是"仓库级"的，不是"需求级"）；且存在静默开启全放行状态的路径 |
| 门拦的不是真问题 | 门拦"没确认就动手"；真正的损失来自"**确认了、但假设是错的**"（实测 3 个 P0 全属此类） |
| 加门有副作用 | 原框架存在每轮无节流注入、要求"整篇重写"某文档的机制 |

⇒ 把资源全压在唯一有效的一关：**写代码前把 5 个问题问完并验完**（半天内）。

## 为什么第 2 步是全文最重的一步

因为要把三件不同的事都解决掉，而且**都不准产文档**：

| 解决什么 | 旧框架里对应什么 | 为何不写文档 |
| --- | --- | --- |
| 用户**不熟悉已有代码库** | `capability-map.md` + teach-back 讲解协议 | 能力地图是一份 md，但**不保证用户懂了**；真正让人懂的是“用伪代码讲 + 用户能复述”这个对话动作。旧框架的协议藏在 `references/teach-back-protocol.md`（本来就不产文档），本包把它写成可直接执行的伪代码 |
| 新方案的**功能取舍** | Decision Log / ADR | 取舍定完只需留**一行负信息**（进代码或知识库）；写表格反而让“讨论”变成“填表” |
| **风险点尚未识别** | 边界清单（10 格）+ 各种调研报告 | 实测：旧框架那份 10 格边界清单**没抓到任何一个 P0**；4 个 P0 全部来自“运行时行为假设 / 接口真实语义 / 硬边界 / 需求名词空档” |

## 唯一的维护动作

**遇到新类型的坑 → 往 `SKILL.md` 的 5 条表里加一行。** 一次一行，不新增文档。

加之前先自问：**没有这条，agent 会做错吗？** 不会 → 删掉它，别加。（官方口径：“通过率不再上升时应当删指令”）
